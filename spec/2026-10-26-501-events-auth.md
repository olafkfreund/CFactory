# Spec: /api/events requires a write-scoped key

## Design

**CFactory: mode-gated WRITE check in the existing middleware.**
`app.py`'s `enforce_api_key` middleware already authorizes `/api/*` with
`authorize_headers(keystore, …, READ)` and skips `/api/events*` via
`_EXEMPT_PREFIXES`. Replace the exemption with a branch for that prefix:
`authorize_headers(keystore, …, WRITE)`. On `HTTPException`:

- mode `warn` (the default): increment a module counter, log one WARNING with
  the path, the status the call would have got (401/403) and the running count,
  then let the request through. The key is never logged.
- any other value, including `enforce`: return the 401/403 JSON response, same
  shape as the rest of `/api`. An unknown value therefore fails closed.

New setting `events_auth_mode: str = "warn"` in `config.py`
(`CFACTORY_EVENTS_AUTH_MODE`), compared after `strip().lower()`. A dev-open
keystore (no keys, `CFACTORY_API_DEV_OPEN=true`) stays open, as everywhere else.

**Strict dev-open parsing.** A `field_validator(mode="before")` on
`api_dev_open` and `mcp_dev_open`: a `bool` passes through; anything else is
`str(v).lower() == "true"`. So `1`, `yes`, `on`, ` true`, `TRUE ` are not open
except exact case-insensitive `true`.

**Senders: `Authorization: Bearer $APP_API_TOKEN`, origin-checked.** Each
sender gets an `_auth_headers(url)` helper copied from PFactory#930
(`agents/handback/send.py`): the token is attached only when `url`'s
`(scheme, netloc)` equals that of the configured `<X>FACTORY_COMPLETION_WEBHOOK`,
and only when `APP_API_TOKEN` is set. Every POST to the webhook adds
`**_auth_headers(url)` to its headers:

- AIFactory: `services/completion.py` (`_notify_worker`,
  `_notify_worker_progress`, `notify_completion`) and `services/outbox.py`
  (relay delivery, whose URL comes from the outbox row — the reason the origin
  check exists).
- PFactory: `agents/triager.py` and `plan/completion.py`.
- TFactory: `agents/triager.py` and `agents/completion_outbox.py`.

`APP_API_TOKEN` is the credential each pod already carries (factory-gitops sets
it from `factory-secrets`), and the #500 review found it equals the cockpit key
in `CFACTORY_API_KEYS`. No new secret, no gitops change.

## Alternatives rejected

- **Enforce now.** Senders deploy separately; an enforce-first rollout drops
  completion events (cost rollups, sequence advances) until all three ship.
- **A dedicated per-factory key.** Better attribution, but needs new secrets in
  three pods and in the keystore; a later rotation can add it without touching
  the CFactory side.
- **Dependency (`require_scope(WRITE)`) on the route.** It cannot express warn
  mode without duplicating the middleware's logic; the middleware already owns
  `/api` auth.
- **Prometheus counter.** CFactory has no metrics endpoint; the running count
  in the log line is enough to prove "zero unauthenticated calls" before the flip.

## Risks

- `APP_API_TOKEN` lacking WRITE scope in `CFACTORY_API_KEYS`: warn mode logs
  every event as 403. That is what warn mode is for; check before the flip.
- A local dev setup with `CFACTORY_API_DEV_OPEN=1` stops being open (it gets the
  401 telling it to set `true`).
- Warn mode accepts events even with no keys configured; only enforce applies
  the #500 fail-closed rule. With an empty keystore and no dev-open,
  `/api/events` stays open in `warn` (each call logged as `would be 401`).
  This is the intended transition state, not a hole closed by this change.
- Log volume in warn mode: one line per event, which is low-rate.

## Verification

- CFactory pytest: warn accepts unauthenticated and keyed events and counts only
  the unauthenticated; enforce returns 401 without a key, 403 with a read-only
  key, 200 with a write key; an unknown mode returns 401; the key never appears
  in logs; dev-open parsing table (`true`, `TRUE`, `True` open; `1`, `yes`, `on`,
  `false`, `` closed) for both flags.
- Each sender: a test that the POST carries the bearer when the URL matches the
  configured origin, and none for another origin or with no token.
