# Spec: CFactory copilot defaults to the current Claude model

## Design

Change the single default `claude-opus-4-8` to `claude-opus-5-5` in:
`apps/backend/cfactory/config.py` (`copilot_model`), `apps/frontend-web/src/SettingsView.tsx` (`defaultModelFor` and the input placeholder), `charts/cfactory/values.yaml`, `.env.example`, `techdocs/dependencies.md`, `techdocs/api.md`, `docs/dev/environment-reference.md`.

Decision (owner delegation): the model field stays a free text input. To "list the new models" it gets a `<datalist>` of suggestions: `claude-fable-5-2`, `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`, then legacy `claude-opus-4-8` (rendered only when `provider === "claude"`). Typing any id still works, so saved and legacy ids are untouched. Reason: smallest change, no allow-list to maintain.

No pricing or cost tables exist in CFactory, so none are added. `runners/github/rate_limiter.py` holds a vendored `claude-sonnet-4-*` price table for another purpose; it is left alone (not a picker, not the copilot).

## Alternatives rejected

- A closed `<select>`: would block saved legacy ids and new releases.
- Shorthand alias map (opus -> id): CFactory passes the id straight to the SDK; no map exists.

## Risks

New default untested on a deployment whose key lacks access: mitigated by the pod proof below, and the setting is editable at runtime. A replaced pod reverts a saved choice to the default (existing behaviour).

## Verification

- Pod proof (2026-11-19): Agent SDK query with `claude-opus-5-5` in the cfactory container returned OK.
- Test asserting the code default is `claude-opus-5-5` (build `Settings` with `_env_file=None` and `CFACTORY_COPILOT_MODEL` unset); existing copilot tests stay green.
- Frontend typecheck/tests per repo CI; helm template renders `CFACTORY_COPILOT_MODEL`.

Checked: neither factory-gitops nor the live ConfigMap sets `CFACTORY_COPILOT_MODEL`, so the production pod takes the code default after the image is bumped.
